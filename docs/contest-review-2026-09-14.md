1. **날씨를 모르는 상태를 정확하게 표시한다. — 해결됨 (2026-09-14)**

   프록시는 날씨 요청 실패 시 12℃·강수확률 20%·풍속 3m/s를 기본값으로 사용하고 ‘날씨가 안정적이에요’라고 반환한다. 앱의 로컬 대체 플랜은 14℃·15%를 사용한다. 실패를 주입해 두 경로를 실제 재현했다. 현재 날짜 선택은 예보 범위를 넘는 미래도 허용한다. Open-Meteo의 예보 제공 범위는 최대 16일이다. [공식 날씨 문서](https://open-meteo.com/en/docs)

   개선: 예보 있음·예보 범위 밖·조회 실패를 구분하고, 뒤의 두 상태에서는 수치와 안전 등급을 미제공으로 표시한다. 조회 시각과 대상 날짜도 함께 보여준다. 이는 지정과제 1번의 날씨 변화 대응에서 잘못된 안내를 막는 기반 기능이다.

   완료 확인: 네트워크 실패, 오류 응답, 예보 범위 밖 날짜에서 고정 날씨 수치나 ‘안정적’ 판정이 나오지 않는다. 프록시 테스트 19개, Flutter 테스트 201개와 프록시 빌드로 확인했다.

   근거: [프록시 기본값](../proxy/api/_weather.ts), [앱 기본값](../lib/planner/plan_models.dart), `lib/main.dart:5196` 날짜 선택 범위.

2. **AI 모델과 실제 생성 여부를 검증한다. — 해결됨 (2026-09-15)**

   기존 프록시는 2026년 6월 1일 종료된 `gemini-2.0-flash`를 지정했다. 모델 호출이 실패해도 프록시의 `source: llm|fallback`을 앱이 버렸기 때문에 사용자는 실제 AI 생성과 기본 규칙 플랜을 구분할 수 없었다. [Google 모델 종료 안내](https://ai.google.dev/gemini-api/docs/deprecations)

   개선: 구조화 출력을 지원하는 안정 버전 `gemini-3.6-flash`로 교체했다. 사고 수준은 `low`, 최대 출력은 4,096토큰으로 제한하고 성공 응답의 입력·출력·사고 토큰 수를 서버 로그에 남긴다. 앱은 응답 출처를 유지해 모델 성공 시 ‘AI 캠핑 플랜’, 서버 또는 로컬 폴백 시 ‘기본 준비 가이드’로 표시한다. [Google Gemini 3.6 Flash 모델](https://ai.google.dev/gemini-api/docs/models/gemini-3.6-flash) [Google 사고 수준 안내](https://ai.google.dev/gemini-api/docs/thinking)

   비용: 무료 등급 키에서는 모델 입력과 출력이 무료다. 유료 등급은 2026년 12월 31일까지 입력 100만 토큰당 0.75달러, 출력과 사고 토큰 100만 토큰당 3.75달러다. 모델 교체만으로 결제가 시작되지는 않으며, 프로젝트에 결제 계정을 연결하고 유료 등급 키를 사용한 경우에 과금된다. 배포 후 성공 요청은 입력 271토큰, 출력 644토큰, 사고 0토큰을 사용했으며 유료 단가 기준 약 0.00262달러다. 실제 배포 키의 결제 등급은 저장소에서 확인할 수 없다. [Google Gemini API 가격표](https://ai.google.dev/gemini-api/docs/pricing) [Google 결제 안내](https://ai.google.dev/gemini-api/docs/billing)

   완료 확인: 모델 URL, JSON 응답 설정, 사고 수준과 출력 상한을 프록시 테스트로 확인했다. AI 응답·프록시 폴백·통신 실패에서 앱의 출처가 구분되고 화면 문구가 달라지는 것을 Flutter 테스트로 확인했다. Azure Functions 배포 후 실제 요청이 `source: llm`으로 성공했고 Application Insights 로그에서 `model=gemini-3.6-flash`와 토큰 사용량을 확인했다. Google API가 503을 반환한 후속 요청은 `source: fallback`으로 정상 전환됐다.

   근거: [모델 호출](../proxy/api/_gemini.ts), [source 응답](../proxy/api/_handler.ts), [앱 응답 처리](../lib/planner/plan_service.dart).

3. **후보 밖 캠핑장이 추천 결과에 섞이지 않게 한다.**

   `coercePlan`은 캠핑장 이름이 비어 있는지만 검사한다. 실제 후보가 ‘실제 후보 A’인 상황에서 모델 결과에 넣은 ‘후보에 없는 가상 캠핑장’이 그대로 통과했다. 화면은 해당 결과를 표시하되 상세 이동은 제공하지 않는다. 후보가 없으면 앱은 ‘강원 인근 캠핑장’ 같은 일반 문구를 추천 항목으로 생성한다.

   개선: 캠핑장 식별자를 요청과 응답에 유지하고, 허용된 후보 집합과 대조한다. 후보가 없으면 빈 상태와 지역 재선택을 제공한다.

   완료 확인: 미등록 이름, 동명 캠핑장, 후보 0건에서 잘못된 추천이 나오지 않고 모든 실제 추천은 해당 상세로 연결된다.

   근거: [결과 검증](../proxy/api/_plan_core.ts), [이름만 전달하는 모델](../lib/planner/plan_models.dart), [상세 이동 조건](../lib/planner/planner_result_screen.dart).

4. **밤하늘 점수를 데이터가 설명할 수 있는 수준으로 표현한다.**

   날씨 없이 달 정보만 계산하는 함수에 달 간섭 0을 넣으면 `hasWeather:false`, 점수 100, ‘은하수까지 보이는 밤’이 반환된다. 카드 제목은 이 등급을 그대로 사용한다. 현재 점수 함수에는 구름·달·바람·기온·강수는 있지만 광공해나 은하수의 관측 위치·시간은 포함되지 않는다.

   개선: 결측 시 ‘달빛 조건만 확인됨’으로 표시하고 종합 관측 점수와 구분한다. 현재 지표로 보장할 수 없는 관측 결과는 단정하지 않는다. 추가 관측 데이터 결합은 그 이후 확장 과제로 둔다.

   완료 확인: 날씨 없음 상태에서 종합 관측 최상위 문구가 나오지 않으며, 각 지수의 근거와 한계를 화면에서 확인할 수 있다.

   근거: [점수와 등급](../lib/tonight/night_models.dart), [카드 제목](../lib/tonight/tonight_card.dart).

5. **선택한 여행을 끝까지 유지한다.**

   홈 밤 미리보기의 ‘이 밤에 갈 캠핑장 보기’는 현재 위치 기반 둘러보기로 연결되며, 선택한 밤의 날짜·장소를 전달하지 않는다. 상세 화면의 `NightPreviewButton`은 선택 여행일을 입력받지 않고 예보 중 `forecast.best`를 사용한다. 상세 호출부에서 인원과 숙련도도 전달하지 않아 기본값인 2명·초보가 사용된다.

   개선: 여행 날짜, 캠핑장 식별자, 좌표, 인원, 숙련도를 공통 여행 정보로 유지하고 밤하늘·플래너·상세·준비 화면에 전달한다.

   완료 확인: ‘특정 날짜, 특정 캠핑장, 4명, 고급’으로 선택한 뒤 모든 화면에서 같은 여행 조건이 유지된다.

   근거: `lib/main.dart:547`, `lib/main.dart:3107`, [상세 밤 미리보기](../lib/preview/night_preview_button.dart).

6. **관광공사 OpenAPI 활용을 추적 가능한 자료로 제시한다.**

   현재 앱은 자체 서버의 캠핑장 API를 호출한다. 이 저장소에는 원천 관광데이터를 수집하는 백엔드 구현이 없어서, 어떤 관광공사 API를 어떻게 수집·갱신하는지 확인할 수 없다. 이는 ‘관광공사 API를 쓰지 않는다’는 판정이 아니다.

   개선: 실제 사용하는 공사 API명, 사용 필드, 원본 식별자와 캠핑장 식별자의 대응, 갱신 주기, 사용 화면을 한 장으로 정리한다. 추천 이유와 데이터 출처도 연결한다. 이미 백엔드에서 관리한다면 그 근거를 출품 자료에 반영하면 된다.

   완료 확인: 시연 캠핑장 한 곳을 원본 데이터부터 추천·상세 화면까지 추적할 수 있고 최신 갱신 시점이 확인된다.

   근거: [개발 기록](../DEVELOPMENT_NOTES.md), `lib/main.dart:6779`, `lib/main.dart:7335`. 공사 OpenAPI 필수 활용은 [공식 공고](https://www.gjto.or.kr/boardDownload.es?bid=0003&list_no=10008&mid=a10201020000&seq=1)에 명시돼 있다.

7. **자연어 요구가 실제 검색 조건을 바꾸게 한다.**

   플래너는 입력 전에 선택 지역 반경 10km에서 후보 10개를 받는다. 자연어를 입력해도 지역·날짜·인원은 기존 조건을 그대로 전송하며, 프롬프트에는 후보 중 처음 5개만 들어간다. 가족 동반 여부는 화면에서 받지만 일반 추천 요청과 AI 플래너 요청 모두에 포함되지 않는다.

   개선: 입력에서 파악한 조건을 칩으로 확인하고 해당 조건으로 후보를 다시 검색한다. 제약 충족 여부와 추천 이유가 같은 데이터를 사용하게 한다. 한 줄 해석을 구현하기 어렵다면 지원하는 자유 입력 범위를 명확히 설명하는 것이 최소 수정안이다.

   완료 확인: 기본 지역과 다른 지역을 입력했을 때 후보도 바뀌고, 가족 동반·장비·교통 조건이 요청 및 추천 근거에 일관되게 반영된다.

   근거: `lib/main.dart:465`, `lib/main.dart:573`, `lib/main.dart:6824`, [자연어 입력 처리](../lib/planner/planner_input_screen.dart), `proxy/api/_plan_core.ts:79`.

8. **여행 준비 상태를 저장한다.**

   즐겨찾기는 로컬 저장되지만 여행 조건, AI 플랜, 체크 상태, 튜토리얼 완료, 야간 테마는 메모리에 둔다. 여행 준비 중 앱을 종료하는 실제 사용을 지원해야 한다.

   개선: 우선 최근 여행 하나와 체크 상태를 로컬에 저장하고 복원한다. 공유·여러 기기 동기화는 후순위 확장으로 둔다.

   완료 확인: 플랜 생성과 준비물 체크 후 앱을 완전히 종료해 다시 열어도 상태가 유지되고, 새 여행을 만들면 이전 여행의 체크 상태와 구분된다.

10. **캠핑장 위치와 숙박 시간에 맞는 예보를 사용한다.**

    개선: 최종 선택 캠핑장의 좌표와 실제 숙박 시간으로 날씨를 조회하고, 지역 참고 예보와 캠핑장 예보를 구분한다.

12. **기다리는 상태와 실패 복구를 실제 요청에 맞춘다.**

    홈에서 플래너를 누르면 후보 조회를 기다린 뒤 입력 화면으로 이동한다. 플랜 요청은 연결 시간 제한만 설정하고 전체 응답 완료에 대한 제한은 두지 않는다. 진행률은 20초 타이머 기반이며 실제 스트리밍 진행률이 아니다. 이번 검토에서는 실제 지연시간이나 무한대기 발생을 측정하지 않았다.

    개선: 즉시 진입 피드백, 후보 조회 상태, 전체 요청 제한시간, 취소·재시도를 제공한다. 실제 진행 상태를 알 수 없는 구간은 진행률의 의미를 오해하지 않게 표현한다.

    완료 확인: 늦은 응답·응답 중단·뒤로가기·재시도에서 화면이 복구되며, 실제 배포 환경에서 생성시간의 중앙값과 상위 95% 지연시간을 측정한다.

    근거: `lib/main.dart:454`, `lib/planner/plan_service.dart:17`, `lib/planner/planner_input_screen.dart:311`.

13. **관광데이터로 캠핑 전후의 지역 방문까지 연결한다.**

    현재 플랜의 일정은 설치·식사·취침·철수 중심이고 주변 관광지·지역 음식점·행사를 묶는 흐름은 확인되지 않는다. 이는 신규 제안이다.

    개선: 우선 시연 지역 한 곳에서 캠핑장과 인근 관광지·음식점 등을 엮은 1박 2일 코스를 만든다. 날씨 악화 시 실내 대안도 제안하되, 장소명·운영정보·이동시간을 실제 데이터로 확인한다. 관광공사 국문 관광정보는 지역·위치 기반 정보와 행사 등을 제공한다. [관광공사 데이터 안내가 포함된 공공데이터포털 자료](https://www.data.go.kr/tcs/puc/selectPublicUseCaseView.do?prcuseCaseSn=1073256)

    완료 확인: 각 추천 장소의 원본 식별자가 있고, 여행 날짜·이동수단·방문 가능 시간에 맞는 실행 가능한 코스 한 개를 끝까지 시연한다.

14. **사용자 효과를 비교 실험으로 보여준다.**
